How to Design an SQL Database for a College Project: ERD to Queries

A well-designed relational database is the backbone of any software engineering or IT project. Learn how to draw Entity-Relationship Diagrams (ERDs), normalize tables from 1NF to 3NF, write clean SQL DDL, and craft performant JOIN queries.

Database design is a fundamental competency evaluated across computer science, information systems, and software engineering coursework. Many college students jump straight into writing `CREATE TABLE` scripts in MySQL, PostgreSQL, or SQLite without formal modeling, resulting in data redundancy, update anomalies, and broken foreign key references.

In this guide, we walk through the complete lifecycle of academic database design: conceptual Entity-Relationship (ER) modeling, relational normalization through Third Normal Form (3NF), declarative schema definition, and multi-table query construction.

1. Conceptual Modeling: Entities, Attributes & Cardinality

Before writing a line of SQL, identify the core real-world concepts in your project brief:

Entities (Nouns)

Objects about which data is stored (e.g., Students, Courses, Enrollments, Instructors).

Attributes (Characteristics)

Properties describing an entity (e.g., student_id, email, gpa, enrollment_date).

Cardinality (Relationships)

How entities relate: One-to-One (1:1), One-to-Many (1:N), or Many-to-Many (M:N, requiring a junction table).

2. Database Normalization: 1NF, 2NF, and 3NF Explained

Normalization eliminates data redundancy and prevents update, insertion, and deletion anomalies. Academic grading rubrics almost always require Third Normal Form (3NF):

First Normal Form (1NF): Atomic Values Each column must hold a single indivisible value. No repeating groups or comma-separated lists (e.g., a student record with 'Math, Physics, CS' in one column violates 1NF).
Second Normal Form (2NF): Full Functional Dependency The table must be in 1NF, and every non-key attribute must depend on the entire primary key, not just part of a composite key.
Third Normal Form (3NF): No Transitive Dependencies The table must be in 2NF, and non-key attributes must depend only on the primary key (no A → B → C dependencies). For example, department name belongs in a Departments table, not repeatedly alongside student records.

3. Writing Clean DDL and Multi-Table JOIN Queries

When writing your SQL schema, enforce data integrity with primary keys, foreign keys, unique constraints, and check clauses:

CREATE TABLE students (
    student_id SERIAL PRIMARY KEY,
    first_name VARCHAR(50) NOT NULL,
    last_name VARCHAR(50) NOT NULL,
    email VARCHAR(100) UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE enrollments (
    enrollment_id SERIAL PRIMARY KEY,
    student_id INT NOT NULL REFERENCES students(student_id) ON DELETE CASCADE,
    course_id INT NOT NULL REFERENCES courses(course_id),
    grade VARCHAR(2) CHECK (grade IN ('A', 'B', 'C', 'D', 'F'))
);

When reporting queries, demonstrate analytical mastery using INNER JOIN, LEFT JOIN, aggregate functions (COUNT, AVG), and GROUP BY ... HAVING clauses.

Frequently Asked Questions

A Primary Key uniquely identifies each record in its own table and cannot contain null values. A Foreign Key is a field in one table that points to the Primary Key of another table, enforcing referential integrity between related entities.

Composite primary keys (formed by two or more columns) are ideal for junction tables representing Many-to-Many relationships, such as linking student_id and course_id together to ensure a student cannot be enrolled in the same course twice.

Standard industry tools like draw.io (diagrams.net), Lucidchart, MySQL Workbench, or dbdocs.io produce clean, professional Crow's Foot notation diagrams suitable for academic report submission.
